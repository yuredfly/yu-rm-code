## 一、学习重点：这一周真正要带走的能力

### 1.1 五个核心重点（按重要性排序）

| # | 重点 | 具体表现 | 为什么最重要 |
|---|---|---|---|
| **1** | **"先看中间产物"的习惯** | 每一步都存图 + 打印 `countNonZero`，再看下一步 | 本周所有难题都不是"函数不会用"，而是"**不知道哪一步开始错的**"。中间产物是你唯一的真相来源 |
| **2** | **mask 决定一切** | 白=前景、黑=背景；目标在 mask 里是黑 → 轮廓必为 0 | 引导原文："后续形态学和轮廓是否有效，很大程度取决于 mask 是否分对" |
| **3** | **形态学的"独立输入"纪律** | 四种操作四次从同一张 mask 出发，**禁止链式** | 链式会让四张图互相污染，**你看到的变化无法归因**。这是本周唯一的"一等一"硬约束 |
| **4** | **参数要能被解释，不能靠抄** | 阈值 120 为什么对（绿 87 < 120 < 背景 248）；HSV 上界 85 为什么能排掉黄色（黄 H=25） | 方案一给了参数，但**方案二不给**。只有理解"参数从哪来"，才能迁移到新图 |
| **5** | **异常路径也是功能** | 读图失败要提示并结束；无目标要输出 0 而不是崩溃 | 任务专门设了这两项测试，说明"程序不崩"和"结果正确"是两件事 |

### 1.2 按知识模块的重点清单

| 模块 | 必须掌握 | 可以暂时不深究 |
|---|---|---|
| 读图 | `imread` 失败不抛异常 → 必须 `empty()`；相对路径基准是**运行目录** | Unicode 路径、EXIF 旋转 |
| 滤波 | 高斯 = 一般平滑；中值 = **孤立小点**；核取正奇数；**必须用滤波结果去分割** | 双边滤波、频域滤波 |
| 阈值 | `BINARY` / `BINARY_INV` 的方向判断（**目标比背景暗 → INV**） | Otsu、自适应阈值 |
| 颜色 | **H ∈ 0–179**（不是 0–360）；`inRange` 输出天然是单通道二值图；**一次只调一个上下界** | 颜色直方图、两段 H 拼接（红/紫跨环） |
| 形态学 | 腐蚀缩小、膨胀扩大、**开=先腐后膨（去小白点）**、**闭=先膨后腐（填小黑孔）**；核大小决定强度 | 顶帽/黑帽/梯度/击中击不中 |
| 轮廓 | `RETR_EXTERNAL` + `CHAIN_APPROX_SIMPLE`；`contourArea` 单位是**像素平方**；传 `clone()` | 轮廓层级 `hierarchy`、凸包 |
| 测量 | `boundingRect`（轴对齐）vs `minAreaRect`（最小旋转）；**`m00 != 0` 才做除法** | `RotatedRect::angle` 的版本语义 |
| 输出 | `imwrite` 要检查返回值、目录要提前存在；`cv::Scalar` 是 **BGR** 顺序；画在原图副本上 | 编解码参数、压缩质量 |

### 1.3 三个"认知层面"的收获（比函数更重要）

| 认知 | 一句话 | 证据 |
|---|---|---|
| **分割是"选择"而不是"计算"** | 灰度与 HSV 是两种**不同的假设**（靠明暗 vs 靠颜色），没有谁绝对更好，只有谁更适配当前图 | 本图两者都能得到 6 个主体；但黄色 H=25 落在 HSV 区间外 → HSV 对"颜色不同"的干扰更干净 |
| **面积是可靠的判据，但必须"看分布"** | 不要先定阈值再验证，而要**先打印全部候选面积**，让数据告诉你分界在哪 | 方案一：主体 5030~19792 vs 小点 4~16，**相差三个数量级** → 阈值 100 极其安全 |
| **几何先验能救算法** | 当像素分割不可靠时，用"结构上的不变量"（等间距、统一尺寸）反推目标 | 方案二详见第三节 |

## 二、我的调试策略（可直接执行的流程）

### 2.1 四步法总览

```
① 可观测化  →  ② 倒查排序  →  ③ 单变量定位  →  ④ 验证闭环
（先把现象变成数字）（从最可能的层往回查）（一次只改一个东西）（改完必须重跑确认）
```

### 2.2 ① 可观测化：每个阶段固定打印一个"验证量"

| 阶段 | 打印什么 | 方案一期望值 | 方案二（原神图）期望值 |
|---|---|---|---|
| 读图 | `cols / rows / channels()` | 960 / 640 / 3 | 1920 / 1200 / 3 |
| 两条路线 | 两次 `countNonZero(mask)` | 67789 / 70180 | 金色像素 7529 |
| 形态学 | 原、腐、膨、开、闭 五个 `countNonZero` | 70180 / 67014 / 73442 / 70152 / 70238 | — |
| 检测 | 候选数量（过滤前） | 12 | 10 条星级条 |
| 过滤 | 过滤后数量 + 被过滤的最大面积 | 6 / 16 | 10 |
| 测量 | 每个目标的面积 + 中心点 | 6 行 | 10 行 + 星级 |
| 保存 | 每次 `imwrite` 的返回值 | 9 次成功 | 2 次成功 |

**原则**：**能在终端打印成数字的，就不要靠肉眼看图**；数字先对，再看图确认形状。

### 2.3 ② 倒查排序：现象 → 先怀疑哪一层

| 现象 | 先查（从外到内） | 不要先动 |
|---|---|---|
| 程序启动即退出 | 工作目录 / 相对路径 | 算法 |
| `[ERROR] Failed to read image` | 文件名、扩展名、运行目录 | 阈值参数 |
| mask 全黑/全白 | 阈值方向与数值、HSV 上下界 | 轮廓、绘图 |
| mask 里目标是黑的 | 阈值类型选反（`BINARY` vs `INV`） | 面积阈值 |
| 轮廓数 = 0 | mask 是否单通道、目标是否白色 | 中心点、外接框 |
| 轮廓数 = 12（方案一） | 轮廓输入是不是 `opened`（应去掉小绿点） | 面积阈值 |
| 轮廓数 20+ | 面积阈值太低 / 开运算核太小 | 绘图 |
| 两个目标被当成一个 | 它们在 mask 里是否已连通；膨胀或闭运算是否过强 | 面积阈值 |
| 框/中心点位置不对 | 坐标是否来自同一张图；x/y 是否写反 | 分割参数 |
| 中心点是 `nan` | 是否先判 `m.m00 != 0` | 绘图函数 |
| 图没保存 | `output/` 是否存在；`imwrite` 返回值 | 图像内容 |
| **改了代码但现象不变** | **是否真的重新编译了**（见 2.5 的踩坑记录） | 任何算法参数 |

**铁律**：**mask 不对就先别调轮廓；数量不对就先别调中心点**（引导原文）。
**原因**：轮廓只消费 mask；测量与绘图**不会改变轮廓数量**。越往后调，越是在给错误的分割打补丁。

### 2.4 ③ 单变量定位法

| 做法 | 说明 |
|---|---|
| **一次只改一个参数** | 尤其是 HSV 的 6 个数（下界 3 + 上界 3）：一次只动一个，才知道是谁起了作用（引导原文） |
| **改动前先记录原值** | 建议在代码里把参数集中在"参数区"，测试时改一处、测完改回来 |
| **二分定位** | 若怀疑某一步，把它临时替换成"已知正确"的中间结果（如直接用 `mask_hsv` 替代 `opened`）看现象是否变化 |
| **用"差分"验证** | 形态学四张图各自的 `countNonZero` 应该**互不相同**；若 `腐蚀 == 开运算`，几乎可以断定链式调用了 |
| **注入断言式检查** | 例如 `cv::countNonZero(mask)` 接近 0 或接近全图时，直接打印警告（本项目 `print_image_info` 就做了尺寸断言） |

### 2.5 ④ 验证闭环：改完必须"重新跑通 + 恢复"

| 环节 | 动作 |
|---|---|
| 编译 | 确认编译日志里**出现了被改动的 .cpp**（没出现 = 没重编译，见下） |
| 跑通 | 重新运行并对照 2.2 的期望值 |
| 恢复 | 测试用的临时改动（HSV 范围、文件名、缩放）**全部撤销** |
| 复跑 | **用原图原参数再跑一次**，让提交的结果图对应原图（任务硬性要求） |

> **本次实测踩到的大坑（务必记住）**
> 我用"文件改名/移动"的方式恢复源码后，MSVC 依据**文件时间戳**判断无需重编译，
> 结果运行的一直是**旧参数**的可执行文件（现象：参数明明改回去了，结果仍是 0）。
> **规避办法**：恢复源码后更新其修改时间，或直接用 `cmake --build build --config Release --clean-first`，
> 并且**在终端确认编译日志里出现了对应的 .cpp 文件名**。

### 2.6 编译期问题速查

| 报错/现象 | 根因 | 解法 |
|---|---|---|
| 中文注释导致语法错误（MSVC） | 文件是 UTF-8，MSVC 按 GBK 解析 | `target_compile_options(目标 PRIVATE /utf-8)` |
| 找不到 `opencv_world4140.dll` | 运行时找不到 DLL | 把 `C:\RM\opencv\build\x64\vc16\bin` 加入 PATH |
| Debug 崩溃 / Release 正常 | 链接了错误配置的库 | Debug 用 `opencv_world4140d.lib` |
| `medianBlur` 断言失败 | ksize 传了偶数或传了 `Size` | 传 `int` 奇数 |
| `findContours` 报错 | 输入不是单通道二值图 | 确认输入是 `CV_8UC1` 的 mask |
| 改了参数但结果不变 | **没重新编译** | `--clean-first`，并确认日志里有该 .cpp |

## 三、方案二（原神截图）的三个特别收获

### 3.1 难点：辉光让"卡片"在像素级连成一片

实测：整卡区域的灰度阈值（105）只得到 **1 个连通域**（`x 203..1692, y 320..900`），
原因是每张卡背后的彩色辉光（5 星金、4 星紫、3 星蓝）在像素级相互连通。
**结论：这张图的 10 张卡不能用"亮度阈值 + 连通域"直接分开** —— 这本身就是值得写进说明文档的发现。

### 3.2 解法：用"颜色锚点 + 几何不变量"反推

| 步骤 | 做法 | 实测结果 |
|---|---|---|
| ① 找锚点 | HSV 金色掩膜（H 18–38, S≥140, V≥150），列投影分组 | 得到 **10 条**星级条，与 10 张卡一一对应 |
| ② 定几何 | 相邻锚点间距**恒定 146.4 像素**；卡片为**统一尺寸**（宽≈147、高≈618，比值≈4.2） | 等价于"卡片是等间距规则排列的矩形" |
| ③ 推边界 | 横向按相邻锚点**中点切分**（保证无重叠同宽）；纵向先找底边再按长宽比推高度 | 10 张卡区域完全一致：`y 296–846`，宽 147–148 |
| ④ 验证 | 卡内平均亮度 − 卡外平均亮度 作为"这确实是卡片"的判据 | 全部通过（差值 22.8~67.9） |

**这一节的方法论最值钱**：**像素不可靠时，改用结构不变量**（等间距、统一尺寸、颜色锚点）。

### 3.3 难点：星星连成一条，"数个数"数不出来

实测：五颗星在金色掩膜里**与一条横向金条连成一体**（星条中部行几乎被金色填满），
8 邻域连通域只能得到 **1 个**，用 9 像素横向腐蚀也切不开。

**解法：把二维问题降成一维信号 —— 列投影峰值计数。**

| 步骤 | 做法 |
|---|---|
| ① | 统计掩膜每一列的金色像素"高度" |
| ② | 只取上半部分高度，避开连成一片的横条（提高峰谷对比） |
| ③ | 宽度**自适应**的滑动平均平滑（`宽/25`，至少 1） |
| ④ | 用峰值 55% 的门槛切段，段数就是星星个数 |

**实测结果**：卡片 1 是 **5 星**、卡片 2–4 是 **4 星**、卡片 5–10 是 **3 星**
→ 星级分布：**5 星 1 张、4 星 3 张、3 星 6 张**。

**缩半测试（任务测试④）的教训**：把图缩到一半后最初只数出 4 张卡 + 星级全错。
原因是**与尺寸耦合的参数没有跟着缩放**：
· `min_group_width = 30` 把缩半后只有约 28 像素宽的星级条整条滤掉了；
· 平滑窗固定为 5 像素，而缩半后相邻星的间距只有约 9 像素，谷底被抹平 → 多星连成一段。
**结论：凡是"像素数量"型参数（最小宽度、面积门槛、核大小、平滑窗）都必须随缩放比例调整**，
线性尺寸按 `s` 缩放、面积按 `s²` 缩放。修正后缩半同样得到 **10 张卡、星级分布一致**。

## 五、一句话总结

**这一周你真正学到的不是 12 个 OpenCV 函数，而是一条完整的工程方法：**
**先把数据打印出来（可观测化）→ 从最可能出错的层往回查（倒查排序）→ 一次只改一个变量（单变量定位）→ 改完必须重跑并恢复（验证闭环）；**
**当像素分割靠不住时，退一步用颜色锚点和几何不变量（等间距 / 统一尺寸）去反推目标。**
